You send ₹1000 to a friend on UPI. Now imagine the bank's server crashes **exactly halfway** through. Your account was debited, but your friend's was never credited. Where did the money go?

In real life this (almost) never happens, thanks to four letters that come up in every backend interview: **ACID**. Let's understand them in simple words.

![ACID: Atomicity, Consistency, Isolation, Durability](/images/blog/acid-cover.svg)

## The ₹1000 problem 🏦

A transfer from account **A** to account **B** is really two steps:

1. Subtract ₹1000 from A.
2. Add ₹1000 to B.

If the server crashes between them:

![Animated: A is debited, the server crashes, B is never credited](/images/blog/acid-bank-crash.svg "Two updates, one crash, ₹1000 gone.")

A lost ₹1000 and B never got it. We need a way to tell the database: *"These two steps belong together. Do both, or neither."* That's a **transaction**.

## What is a transaction?

> **A transaction is a group of database operations treated as one unit. Either all of them succeed, or none of them take effect.**

Think of it as a **package deal** for your queries. Examples:

- 💸 **Bank transfer:** debit one account + credit another.
- 🛒 **Placing an order:** create the order + reduce stock + record the payment.

Doing only half of any of these leaves the data broken.

### Transactions in SQL

```sql title="transfer.sql"
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE id = 'A';
UPDATE accounts SET balance = balance + 1000 WHERE id = 'B';
COMMIT;
```

| Command | What it does |
| --- | --- |
| `BEGIN` | Starts the transaction. |
| `COMMIT` | Saves everything permanently and makes it visible to others. |
| `ROLLBACK` | Cancels everything since `BEGIN`. |

If something goes wrong halfway, you cancel:

```sql
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE id = 'A';
-- B's account is frozen, so stop
ROLLBACK;   -- A gets its ₹1000 back
```

Every transaction follows the same path and ends in one of two places:

![Flowchart: Active, then Partially committed and Committed, or Failed and Aborted](/images/blog/acid-transaction-states.svg)

<Callout type="info" title="Autocommit">
  A single statement without `BEGIN` runs as its own tiny transaction and commits immediately. That's why one statement is always safe, but two separate statements are not.
</Callout>

## So what exactly is ACID?

Transactions are the tool. **ACID** is the set of four promises the database makes about every transaction:

![The four ACID properties applied to a bank transfer](/images/blog/acid-overview.svg)

**Is ACID a rule, a setting, or default behaviour?**

- It's a set of **guarantees**, not a feature you switch on. There's no `ENABLE ACID;` command. You use transactions, and the database keeps the promises.
- PostgreSQL, MySQL (InnoDB), Oracle and SQL Server provide it **by default**. The one part you can tune is how strict isolation is (more on that below).

Let's go through each letter.

## 1. Atomicity: all or nothing ⚛️

> **Atomicity means a transaction can't be split. Either every step is applied, or none are.**

With atomicity, our transfer has only two possible endings:

![Animated: happy path commits both updates; crash path rolls everything back](/images/blog/acid-atomicity.svg "Both endings keep the total at ₹7,000.")

Atomicity doesn't stop crashes. It guarantees that **a crash can't leave you halfway.** After recovery, the transfer either fully happened or never happened.

### How databases achieve atomicity

The database must be able to undo unfinished work, even after a power cut wipes its memory. The trick: **write everything down before doing it.**

#### Transaction log and WAL

The **transaction log** is the database's diary. Before changing any data, it writes a note: *"tx 735: change A from 5000 to 4000."*

The rule is called **Write-Ahead Logging (WAL)**:

> **The log entry for a change must be saved to disk *before* the change itself is written to the data files.**

Why write the diary first?

1. **It's fast.** The log is append-only: always write at the end of one file. Updating the real table means jumping around the disk, which is slow.
2. **It's enough to recover.** If the diary is safe, everything else can be rebuilt from it.

![Animated: change in RAM, append WAL and fsync, return COMMIT OK, checkpoint later](/images/blog/acid-wal-flow.svg "Log first, data later.")

1. The change is made in **memory**.
2. A log entry is **written to the WAL on disk** and forced to disk (`fsync`).
3. The database replies **"COMMIT OK"**.
4. Later, a **checkpoint** copies the changed data to the real data files.

If the server dies after step 3, nothing is lost: on restart the database replays the WAL.

#### What a real transaction log looks like

PostgreSQL keeps its WAL in the `pg_wal/` folder, and the `pg_waldump` tool prints it in readable form. Here's our transfer (tx 735) and a second transaction that was cancelled (tx 736):

![pg_waldump output showing two updates and a COMMIT for tx 735, and an ABORT for tx 736](/images/blog/acid-real-wal-log.svg "Output format of PostgreSQL's pg_waldump, recreated for readability.")

- **`tx`** is the transaction ID. Both updates share **735**, so the database knows they belong together.
- **`lsn`** is the entry's position in the log. It only goes up, so the order of events is always clear.
- **`desc`** says what happened. The **`COMMIT`** line is the moment tx 735 became real. tx 736 ends in **`ABORT`**, so its change is never shown to anyone.

#### Rollback

A **rollback** puts every row a transaction touched back the way it was. It happens when:

- your code runs `ROLLBACK` (for example, the card was declined),
- the database cancels it (a rule was broken, or two transactions got stuck waiting on each other), or
- the server crashed before `COMMIT`. On restart, unfinished transactions are rolled back automatically.

#### Undo and redo logs

![Undo log stores old values for rollback; redo log stores new values for crash recovery](/images/blog/acid-undo-redo.svg)

- **Undo log = the "before" photo.** It keeps the **old** value so an unfinished transaction can be reversed.
- **Redo log = the "after" photo.** It keeps the **new** value so a committed change can be re-applied after a crash.

After a crash, recovery first **redoes** what's in the log, then **undoes** transactions that never committed.

## 2. Consistency: rules are rules 📏

> **Consistency means a transaction moves the database from one valid state to another. It never leaves data that breaks the rules.**

For our bank, "valid" means: no balance below ₹0, every account has an owner, no duplicate account numbers, and the total money doesn't change during a transfer. If a transaction would break a rule, the whole transaction is rejected and rolled back.

### The rules the database enforces

These are **constraints**, declared when you create the table:

```sql title="accounts.sql"
CREATE TABLE accounts (
  id          SERIAL PRIMARY KEY,
  account_no  VARCHAR(20) UNIQUE NOT NULL,
  owner_email VARCHAR(255) NOT NULL,
  balance     NUMERIC(12, 2) NOT NULL CHECK (balance >= 0),
  branch_id   INT REFERENCES branches(id)
);
```

| Constraint | Guarantees | Fails when you… |
| --- | --- | --- |
| **PRIMARY KEY** | Each row has a unique ID | insert a second row with `id = 1` |
| **NOT NULL** | The column always has a value | leave the email empty |
| **UNIQUE** | No two rows share this value | reuse an account number |
| **CHECK** | A custom condition always holds | set `balance = -500` |
| **FOREIGN KEY** | Links point to rows that exist | use branch 999, which doesn't exist |
| **Data type** | Values match the column type | store `'abc'` in a number column |

```sql
UPDATE accounts SET balance = balance - 10000 WHERE id = 1;
-- ERROR: new row violates check constraint "accounts_balance_check"
```

### How consistency is achieved

Consistency is a **team effort**. The database only knows the rules you told it. It has no idea about your daily transfer limit or KYC checks.

![Two guards: the application layer checks business rules, the database enforces constraints](/images/blog/acid-consistency-gates.svg)

- **Database rules** (constraints, types, foreign keys) are checked on every write, from every source. A buggy deploy can't skip them.
- **The application layer** checks business rules ("max ₹1 lakh per day", "can't send money to yourself"), shows friendly errors, and, importantly, **puts the right steps in one transaction**. If your code commits the debit and credit separately, no constraint can save you.

<Callout type="tip" title="Rule of thumb">
  Validate in the app for a good user experience. Enforce in the database for correctness.
</Callout>

## 3. Isolation: no peeking 🚧

> **Isolation means transactions running at the same time don't interfere with each other. Each one behaves as if it were alone.**

### Why it matters

A flash sale. **2 iPhones left.** Two buyers click "Buy" at the same moment. Each checkout reads the stock, subtracts one, and writes it back:

![Animated: two buyers both read stock 2, both write 1, final stock is 1 instead of 0](/images/blog/acid-lost-update.svg "Two phones sold, but stock only dropped by one.")

Nothing crashed and no rule was broken, yet the result is wrong. That's what happens without isolation.

### The 5 classic problems

| Problem | In one line |
| --- | --- |
| **Dirty read** | You read another transaction's change **before it commits**, and it might be cancelled. |
| **Non-repeatable read** | You read the **same row twice** and get **different values**. |
| **Phantom read** | You run the **same query twice** and **new rows appear** (or vanish). |
| **Lost update** | Two transactions update the same value and **one silently overwrites the other**. |
| **Write skew** | Two transactions read the same data, then update **different rows**, together breaking a rule. |

![Four timelines: dirty read, non-repeatable read, phantom read and write skew](/images/blog/acid-anomalies.svg)

### Isolation levels

Full isolation is slow, because transactions have to wait for each other or retry. So databases offer **isolation levels**.

> **An isolation level decides which of these problems a transaction is protected from.** Stricter levels are safer but slower.

![Matrix of the four isolation levels and which anomalies each prevents](/images/blog/acid-isolation-levels.svg)

In each example, account A starts with ₹5,000.

#### Repeatable Read

> **Once you read a row, it stays the same for the rest of your transaction.**

Your transaction reads from a **snapshot** taken at its first read.

| Step | T1 (Repeatable Read) | T2 |
| --- | --- | --- |
| 1 | reads A → 5000 | |
| 2 | | sets A = 4000, commits |
| 3 | reads A → **5000** (same as before) | |

- ✅ Stops dirty reads and non-repeatable reads.
- **Default in MySQL.**

#### Read Committed

> **You only see committed data, but each query sees the latest committed version.**

| Step | T1 (Read Committed) | T2 |
| --- | --- | --- |
| 1 | reads A → 5000 | |
| 2 | | sets A = 4000 (not committed) |
| 3 | reads A → 5000 (no dirty read ✅) | |
| 4 | | commits |
| 5 | reads A → **4000** (changed mid-transaction) | |

- ✅ Stops dirty reads. ❌ Other problems can still happen.
- A good balance for most web apps.
- **Default in PostgreSQL, Oracle and SQL Server.**

#### Read Uncommitted

> **You can see other transactions' changes even before they commit.**

| Step | T1 (Read Uncommitted) | T2 |
| --- | --- | --- |
| 1 | | sets A = 10,00,000 (not committed) |
| 2 | reads A → **10,00,000** (dirty read) | |
| 3 | | rolls back |

- ❌ Allows everything. Rarely used.

#### Serializable

> **The strictest level. The result is the same as if transactions ran one after another.**

Take the write-skew example: two doctors on call, and at least one must stay. Both check, see 2 on call, and both go off call. Under Serializable, the database spots the conflict:

| Step | Dr. Asha | Dr. Ravi |
| --- | --- | --- |
| 1 | sees 2 on call | sees 2 on call |
| 2 | goes off call | goes off call |
| 3 | commits ✅ | commit **fails**: "could not serialize access" |

Dr. Ravi's app retries, sees only 1 doctor left, and refuses. The rule holds.

- ✅ Stops every problem in the list.
- ❌ Slower, and **your app must retry** failed transactions.
- Use it for money, inventory and bookings, where correctness matters most.

The main difference between the two middle levels is **when the snapshot is taken**:

![Repeatable Read takes one snapshot per transaction; Read Committed takes a new one per query](/images/blog/acid-snapshot-timing.svg)

Not sure which to pick? Use this guide:

![Flowchart for choosing an isolation level](/images/blog/acid-choose-isolation.svg)

### Setting the isolation level

```sql title="PostgreSQL"
BEGIN ISOLATION LEVEL SERIALIZABLE;   -- just this transaction
-- your queries
COMMIT;

SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;  -- whole session
```

```sql title="MySQL"
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;          -- next transaction only
SET SESSION TRANSACTION ISOLATION LEVEL SERIALIZABLE;  -- whole session
```

### How isolation is implemented

![Locks make transactions wait their turn; MVCC gives each reader its own snapshot](/images/blog/acid-locks-mvcc.svg)

#### 1. Locks 🔒

Before touching a row, a transaction locks it.

- **Shared lock:** "I'm reading." Many readers can share it.
- **Exclusive lock:** "I'm writing." Everyone else waits.
- Locks are held until `COMMIT` or `ROLLBACK`.

This fixes the iPhone sale:

```sql
BEGIN;
SELECT stock FROM products WHERE id = 'iphone' FOR UPDATE;  -- lock the row
UPDATE products SET stock = stock - 1 WHERE id = 'iphone';
COMMIT;
```

The second buyer waits, then sees the updated stock. The downside is waiting, and **deadlocks** (two transactions waiting on each other), which the database fixes by cancelling one.

![Animated: Buyer 2 waits for the lock, then reads the updated stock; final stock is 0](/images/blog/acid-for-update.svg "Same sale, now with a lock. Stock ends at 0.")

#### 2. MVCC (Multi-Version Concurrency Control) 📸

Instead of overwriting a row, the database **keeps old versions**. Each transaction reads the version that was committed when its snapshot was taken.

- Readers don't block writers, and writers don't block readers.
- Used by PostgreSQL, MySQL and Oracle. This is how Repeatable Read gives you a "frozen" view.

#### 3. Conflict detection 🕵️

Let transactions run freely, then **check for conflicts at commit** and cancel the loser. PostgreSQL's Serializable level works this way. Apps can do something similar with a `version` column:

```sql
UPDATE products SET stock = stock - 1, version = version + 1
WHERE id = 'iphone' AND version = 7;
-- 0 rows updated? Someone changed it first. Re-read and retry.
```

![Flowchart: read the row, write only if the version is unchanged, otherwise retry](/images/blog/acid-optimistic-retry.svg)

This is fast when conflicts are rare, and wasteful when they're common.

## 4. Durability: commit means forever 💾

> **Durability means once a transaction is committed, it survives crashes, power cuts and restarts.**

When the database says "COMMIT OK" and your app shows a green tick, the transfer is permanent, even if the power goes out a millisecond later.

### Common myths

- ❌ **"It's in the database, so it's durable."** Data only in memory is lost on a power cut. Durable means the change (or its log entry) is **on disk**.
- ❌ **"Durability means no backups needed."** Durability protects against crashes, not a dead disk, a fire or an accidental `DELETE`. For those you need **backups and replicas**.
- ❌ **"Writing a file puts it on disk."** Normal writes often sit in the operating system's memory first. Only **`fsync`** forces them onto the disk.

![A write passes through database memory, the OS cache and the disk cache; only fsync pushes it to disk storage](/images/blog/acid-write-path.svg)

### How durability is achieved: WAL again

1. On `COMMIT`, the database writes the commit entry to the WAL and calls `fsync`.
2. Only after the disk confirms does it reply "COMMIT OK".
3. After a crash, it **replays the WAL** to restore every committed change.

To stay fast, many commits share one `fsync` (**group commit**). To survive losing a whole machine, the WAL is also copied to other servers (**replication**).

### Durability vs speed

Every `fsync` is a small wait. At hundreds of thousands of writes per second, those waits add up, so databases let you choose:

![The durability dial, from never flushing to synchronous replication](/images/blog/acid-durability-tradeoff.svg)

| Setting | On a crash you can lose |
| --- | --- |
| Flush on every commit (**default** in PostgreSQL and MySQL) | Nothing committed |
| Flush about once a second (PostgreSQL `synchronous_commit = off`, MySQL `innodb_flush_log_at_trx_commit = 2`) | About the last second of commits |
| Wait for a second server too (synchronous replication) | Nothing, even if the whole server dies |

<Callout type="danger" title="Don't confuse these">
  `synchronous_commit = off` can lose the last moment of commits. PostgreSQL's **`fsync = off`** can **corrupt the whole database**. Never use it in production.
</Callout>

**🛡️ Durability first**, where losing one record is a disaster:

- payments and UPI
- e-commerce orders
- seat and ticket bookings
- medical records and stock trades

**🚀 Speed first**, where losing the last second is fine:

- analytics and click events
- view counters and likes (like the ones on this blog 👀)
- app logs, metrics and sensor readings
- caches and sessions

The question to ask: **"If the last second of this data vanished, would anyone care?"**

## TL;DR 🧾

- A **transaction** is an all-or-nothing group of operations: `BEGIN … COMMIT` or `ROLLBACK`.
- **Atomicity:** no half-done work. Achieved with WAL, undo logs and rollback.
- **Consistency:** data always follows the rules. Achieved with constraints **and** application logic.
- **Isolation:** concurrent transactions don't corrupt each other. Tuned with isolation levels; built with locks, MVCC and conflict detection.
- **Durability:** "COMMIT OK" means forever. Achieved with WAL + `fsync`, plus replication. You can trade some of it for speed.

Next time a UPI payment shows "pending" for a few seconds, you'll know there's a whole ACID machine making sure your ₹1000 lands exactly once. 😎
