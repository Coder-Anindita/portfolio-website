You're on café Wi-Fi, logging in to your email. Your password travels through routers and networks you'll never see, yet the little padlock 🔒 says you're safe. Let's see why, one problem at a time.

**The cast:**

- 👩‍💻 **Pam** is the client (your browser).
- 🖥️ **Jim** is the server (the website).
- 🕵️ **The hacker** is sitting on the same café Wi-Fi, listening to everything.

<Callout type="info" title="SSL or TLS?">
  SSL is the old name. Today's protocol is called **TLS**, but everyone still says "SSL certificate".
</Callout>

## The problem: HTTP sends everything in plain text

Pam sends a request, Jim sends a response. With plain HTTP, anyone in between can read it:

![Plain HTTP can be sniffed](/images/blog/tls-plain-http.svg "The hacker doesn't need to break anything. Just listen.")

The hacker can **read** the data (passwords, cookies) and even **change** it on the way. We need to stop both, and make sure Pam is really talking to Jim.

## Step 1: Lock it with a key (symmetric encryption)

The obvious fix is to encrypt the data. Using **the same secret key to encrypt and decrypt** is called **symmetric encryption**. It's very fast and very secure.

![Symmetric encryption and the key-sharing problem](/images/blog/tls-symmetric.svg)

But there's a catch. Jim needs the key to read the message. If Pam sends the key over the internet, the hacker just copies it.

> **How do we share a key over a network the hacker is watching, without the hacker getting it?**

## Step 2: Two keys instead of one (asymmetric encryption)

This is where **asymmetric encryption** comes in. Everyone gets a **pair** of keys:

- 🔓 **Public key:** shared openly with everyone.
- 🔑 **Private key:** kept secret, never shared with anybody.

**Whatever is locked with the public key can only be unlocked with the matching private key**, and you can't work out the private key from the public one. Think of the public key as an **open padlock**: anyone can snap it shut, but only Pam's private key opens it.

![Asymmetric encryption](/images/blog/tls-asymmetric.svg)

Pam sends her public key to Jim, Jim locks his message with it, and only Pam can unlock it. The hacker has the padlock and the locked box, but no key. ✅

## Step 3: Proving who sent it (signatures)

Now a different problem. Jim must be **sure a message came from Pam** and that **nobody changed it**. For this, Pam uses a **digital signature**:

1. Pam creates a **hash** of the message using an algorithm like **SHA-256**. A hash is a short fingerprint of the data. Change even one letter, and the hash changes completely.
2. Pam **signs** the hash with her **private key**. That's the signature.
3. She sends the message along with the signature.

Jim then hashes the message himself and checks the signature using **Pam's public key**. If it matches, it's real. If not, it was faked or changed.

![Digital signatures](/images/blog/tls-signature.svg)

Only Pam has her private key, so only she could have made that signature. Notice the keys work the **other way round** here. This is easy to mix up, so here's a cheat sheet:

| You want… | You use… |
| --- | --- |
| **Secrecy:** only Jim can read it | Lock with **Jim's public key**. Jim opens it with his private key. |
| **Proof:** it came from Pam | Pam signs with **her private key**. Anyone checks with her public key. |

## Step 4: Fast and safe together (hybrid encryption)

Asymmetric encryption solves key sharing, but it's **slow**, far too slow for whole web pages. So we use both:

1. Pam creates a random **session key** (a symmetric key).
2. She locks it with **Jim's public key** and sends it.
3. Jim unlocks it with **his private key**.
4. Now both have the same session key, and the hacker doesn't. Everything after this is encrypted with that fast session key.

![Hybrid encryption](/images/blog/tls-hybrid.svg)

This is **hybrid encryption**: the slow part happens once, the fast part handles everything else. (Newer TLS versions even let both sides *calculate* the session key instead of sending it, but the idea is the same.)

Problem solved? Not quite.

## The loophole: the hacker in the middle

Everything above assumes Pam has **Jim's real public key**. But she gets it over the internet, the same internet the hacker is sitting on. So the hacker doesn't break any encryption. They just **swap the keys**:

![Man-in-the-middle attack](/images/blog/tls-mitm.svg)

1. Jim sends his public key. The hacker grabs it.
2. The hacker sends Pam **their own** public key, pretending to be Jim.
3. Pam encrypts her data with the hacker's key, thinking it's Jim's.
4. The hacker decrypts it, reads it, re-encrypts it with Jim's real key and passes it on.

Both think the connection is secure. This is a **man-in-the-middle attack**. The real problem: **a public key is just a big number. Nothing in it says who it belongs to.**

## The fix: SSL certificates and Certificate Authorities

A **Certificate Authority (CA)**, like Let's Encrypt, is an organisation browsers trust to check who owns a website. An **SSL certificate** is a signed note from the CA saying:

> *"This public key belongs to `jim.com`. Valid until January 2027. Signed, Some CA ✍️"*

Here's a real one, the certificate of SBI's internet banking site:

![SSL certificate of onlinesbi.sbi.bank.in](/images/blog/tls-sbi-certificate.png "The certificate viewer for onlinesbi.sbi.bank.in.")

- **Issued To:** the website, `onlinesbi.sbi.bank.in`, owned by State Bank of India.
- **Issued By:** the CA that checked and signed it, DigiCert.
- **Validity Period:** after this, browsers stop trusting it.
- **SHA-256 Fingerprints:** short hashes of the certificate and its public key.

### How Jim gets one

![How a CA issues a certificate](/images/blog/tls-ca-signing.svg)

1. Jim sends his **public key and domain name** to the CA. His private key stays on his server.
2. The CA checks that Jim **really controls `jim.com`**, e.g. by asking him to put a special file on the site.
3. The CA **hashes** the domain, public key and expiry date with SHA-256, and **signs that hash with its own private key**.
4. That data plus the signature is the certificate.

<Callout type="warning" title="The CA's private key is never in the certificate">
  It's easy to think the CA "adds its private key" to the certificate. It doesn't. The private key never leaves the CA. Only the **signature** made with it goes into the certificate.
</Callout>

### How the browser checks it

When Pam connects, Jim sends his certificate. Pam's browser hashes the data itself and checks the CA's signature using the **CA's public key**. If it matches, the certificate is genuine and untouched.

![How the browser verifies a certificate](/images/blog/tls-cert-verify.svg)

But can't the hacker swap the CA's public key too? No! The CA's public key **never comes over the network**. Your operating system and browser already ship with a built-in list of trusted CAs, called the **trust store**. The browser also checks that the certificate is for the **domain you opened** and hasn't **expired**.

### One last trick the hacker might try

Certificates are **public**, so why can't the hacker just send Jim's real one? Because during the connection, Jim's server also **signs some data with its private key**, and Pam checks it with the public key in the certificate. The hacker doesn't have that private key.

And their **own** certificate for `jim.com`? No CA will issue one, because they can't prove they own the domain. Big red browser warning. 🚫

## Putting it all together

When you open an `https://` site, all of this happens in a few milliseconds. Here's how each problem got solved:

| Problem | What fixes it |
| --- | --- |
| Hacker reads the data | Encryption |
| How to share the key safely | Asymmetric encryption (hybrid) |
| Hacker changes the data | Hashes and signatures |
| Hacker swaps in their own public key | Certificate signed by a trusted CA |
| Hacker sends Jim's real certificate | Server proves it has the private key |

<Callout type="tip" title="Try it yourself">
  Click the icon next to the URL in your browser and open the certificate details. You'll see who it was issued to, which CA signed it, and when it expires.
</Callout>

## One thing the padlock doesn't mean

The padlock means your connection to **that website** is private, not that the website is safe. A phishing site like `paypa1-login.com` can get a valid certificate too. Always check the URL. 👀

## TL;DR 🧾

- **Symmetric:** one fast key, but sharing it is the problem.
- **Asymmetric:** public key locks, private key unlocks.
- **Signatures:** sign with your private key, others verify with your public key.
- **Hybrid:** asymmetric once to share a session key, then symmetric for everything.
- **Certificates:** a CA's signed note that "this public key belongs to this website", checked against CAs your device already trusts.

Next time you see that padlock at a café, you'll know why the hacker sees nothing but gibberish. 😎
